# 프롬프트·스킬·템플릿 — 필요한 만큼 쓰기

**기존 시작 문구는 그대로 쓴다.** 이 문서는 요청 범위·출력 형식이 모호하거나 AI 결과를 개선할 때만 참고한다. 사용자가 새 문구를 외우거나 양식을 먼저 채울 필요는 없다. 실제 과제 지시·제공 자료·이미 받은 답을 우선한다.

## 1. 무엇이 다른가

| 이름 | 뜻 | 이 자료집에서의 예 |
| --- | --- | --- |
| 프롬프트 | 지금 AI에게 맡기는 요청 | 지시서를 읽고 요구와 확인 질문을 정리하라는 시작 문구 |
| 컨텍스트 | 판단에 필요한 자료·대화·현재 상태 | 실제 지시서, 입력 파일, 담당자 답변, 기존 WORKLOG |
| 템플릿 | 필요한 항목을 빠뜨리지 않도록 만든 재사용 양식 | [작업 요청 빈 양식](../templates/TASK_REQUEST.template.md), [작업 기록 빈 양식](../templates/WORKLOG.template.md) |
| 스킬 | 적용 상황과 반복할 절차·판단 기준을 묶은 지침 | 기존 [task-evidence-check](../skills/task-evidence-check/SKILL.md) 하나 |

요청 템플릿은 **무엇을 맡길지**, WORKLOG는 **실제로 무엇을 했는지** 정리한다. 양식을 채웠다는 사실이 실행·검증 완료의 근거는 아니다. 방법론 MD를 AI에게 읽히는 것과 호스트에 스킬이 등록되는 것도 다르다.

## 2. 프롬프트를 구체화하는 순서

프롬프트 엔지니어링은 요청과 필요한 맥락을 정리하고, 실제 결과를 확인해 개선하는 작업이다. 아래 항목 중 현재 자료에 부족한 것만 보완한다.

| 항목 | 적을 내용 | 확인할 점 |
| --- | --- | --- |
| 목적·요청 범위 | 누구의 어떤 일을 돕는지, 생성·수정·검토·설명 중 무엇을 맡기는지 | 검토 요청을 파일 수정으로 확대하지 않음 |
| 입력·근거 | 실제 지시서와 데이터의 위치, 관련 기간·범위, 받은 답 | 경로를 썼다는 것과 AI가 실제 읽었다는 것을 구분 |
| 규칙·제약 | 원문에서 확인된 기준·예외·허용 도구·보존할 입력 | 미확인·AI 제안·사용자 결정과 분리 |
| 출력 | 파일명·열·형식·정렬·길이 등 과제에 필요한 항목 | 과제가 열어 둔 선택을 필수 조건으로 만들지 않음 |
| 확인 기준 | 무엇과 대조해 맞다고 볼지, 확인할 수 없는 것은 어떻게 표시할지 | 기준과 기대 결과를 AI가 임의로 확정하지 않음 |

예를 들어 요청을 “분석해줘”에서 “지정한 파일을 읽고 확인된 기준으로 요약한 뒤, 결과와 원자료를 대조해 근거·한계를 알려줘”로 구체화할 수 있다. 실제 파일·기준·출력은 지시서에서 가져오며 모르는 값은 만들어 넣지 않는다. 명확한 지시·관련 맥락·출력 예시를 제공하는 원칙은 [OpenAI 공식 Prompt engineering 안내](https://developers.openai.com/api/docs/guides/prompt-engineering)를 참고했다.

## 3. 기법은 문제가 있을 때 선택하기

| 기법 | 쓰는 때 | 적용 범위 |
| --- | --- | --- |
| 지시와 자료 구분 | 요청문과 인용 자료가 섞여 혼동될 때 | 제목·목록·구분자로 목적/지시/원자료를 나눔. 구분자 자체가 보안 차단 기능은 아님 |
| Zero-shot | 예시 없이도 목표와 기준이 충분할 때 | 먼저 명확한 요청으로 진행. 모든 과제에 예시를 만들지 않음 |
| Few-shot | 원하는 추출·분류·표현 형식을 계속 놓칠 때 | 사용이 허용된 입력/출력 예시 몇 개로 형식을 설명. 예시와 실제 규칙의 충돌을 확인 |
| 출력 형식 지정 | 후속 처리나 제출 형식이 정해져 있을 때 | 필요한 열·필드·단위 등을 지정. CSV/JSON 형식이 맞아도 값은 별도 검증 |
| 작업 나누기 | 서로 다른 요구나 선행 작업이 있을 때 | 필요한 단위로 나누고 합친 결과도 확인. 역할 분리는 [방법 안내 4절](interview-qa-methods.md#4-역할-분리-작업과-검토의-관점-나누기) 사용 |
| 관측에 따른 수정 | 결과가 요구와 다를 때 | 기대·실제 차이와 원문 근거를 알려 부족한 지시만 보완하고 관련 검사를 다시 수행 |

추론 모델에는 짧고 직접적인 지시부터 사용하고, 예시나 추가 절차는 필요할 때 보완한다. 긴 사고 과정의 출력을 요구하는 대신 **판단 요약·사용한 근거·실제 검사 결과·한계**를 요청한다. [OpenAI 공식 Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

조건을 추가하기 전에 실패 원인이 입력 누락·업무 기준 미확인·코드 오류·검사 오류인지 살핀다. 업무 기준이 없으면 인터뷰로 확인하고, 이미 명확한 규칙을 코드가 어겼다면 구현을 고친다. 문제와 무관한 긴 지시를 계속 덧붙이지 않는다. 개인 사전 연습에서 문구를 비교할 때는 같은 입력과 확인 기준으로 관측하고, 한 번의 좋은 결과를 모든 과제의 성능으로 확대하지 않는다.

## 4. 언제 스킬로 묶는가

여러 작업에서 **같은 적용 조건·판단 기준·예외 처리**가 반복되고 기존 지침과 역할이 겹치지 않을 때 고려한다. 한 번의 요청은 프롬프트, 반복해서 바뀌는 값은 템플릿, 공통 수행 원칙은 스킬로 정리할 수 있다. 이 자료집은 기존 스킬 하나로 충분하며 이번 보완은 참고 MD와 빈 양식이다.

스킬 구조의 **사전 학습용 빈 예시**다. 실제 스킬 파일이나 설치 명령이 아니며, 응시 중 새로 생성·등록할 단계로 사용하지 않는다.

```markdown
---
name: my-workflow
description: "어떤 반복 업무를 언제 수행하는지 적는다."
---
입력: 필요한 자료와 확인된 조건
절차: 요청된 범위에 맞는 핵심 수행 순서와 판단 기준
확인: 관찰 가능한 완료 기준과 미확인 처리
결과: 사용자에게 줄 산출물·근거·한계
```

실제 작성할 때는 이름·설명에 업무와 적용 상황을 구체적으로 적고, 본문에 입력·수행·확인·종료 범위를 둔다. 참고 파일·스크립트·템플릿은 필요할 때만 추가한다. 이 구조는 [OpenAI 공식 Build skills 안내](https://developers.openai.com/plugins/build/skills)를 참고했다. 호스트별 발견·등록 방식은 별개이며 현재 Probe의 자동 등록을 가정하지 않는다.

## 5. 템플릿 사용과 개선 요청

[작업 요청 빈 양식](../templates/TASK_REQUEST.template.md)은 누락 점검용이다. AI가 이미 읽은 지시서·대화에서 필요한 항목을 먼저 정리하고, 결과를 바꾸는 미확인만 질문한다. 모든 칸을 채울 때까지 작업을 막거나 사용자가 같은 내용을 다시 작성하게 하지 않는다.

채운 내용은 허용된 과제 채팅에서 사용한다. 저장이 필요하면 기존 과제 기록에 연결하고 매 요청마다 새 파일을 만들지 않는다. 공개 원본 양식에는 실제 문제·데이터·답변·응시 정보를 적거나 push하지 않는다. 별도 인터뷰·QA 양식은 추가하지 않고 [기존 방법 안내](interview-qa-methods.md)와 WORKLOG를 쓴다.

요청 정리·잘못된 결과 보완용 선택 문구는 [RUNBOOK](../RUNBOOK.md#프롬프트와-요청-템플릿이-필요할-때)에 있다. 통합 시작 문구로 진행 중이면 AI가 필요에 따라 적용하므로 따로 입력할 필요 없다. 실제 서술형처럼 AI가 금지된 단계에는 사용하지 않는다.

확인일: **2026-10-31**. 위 공식 문서의 관련 본문을 직접 읽었다. 요청 범위 구분·한 개의 기록·미확인 처리·이 자료집에 맞춘 빈 양식은 작성 제안이며, API 설정·모델 변경·추가 설치를 요구하지 않는다. 특정 문구의 실제 Probe 성능이나 점수를 검증한 자료가 아니다.

## 6. 모델과 추론 수준 쉽게 고르기

**이미 잘되면 현재 모델·추론 설정을 유지한다.** 처음 선택해야 하고 제공·허용이 확인됐다면 **Sol 6.1 + Medium**을 출발점으로 고려한다. 이는 이 자료집의 실용 제안이며 모든 환경의 기본값은 아니다. 선택 기능이 없거나 불명확하면 설정을 찾느라 작업을 멈추지 않는다.

아래는 **공개 모델 설명에 근거한 사용 예시**다. Cofa의 제공 목록·공식 권장 설정이 아니며, 화면에 실제로 있고 현재 안내가 허용한 항목만 선택한다. 세부 배정은 작성 제안이다.

| 모델 | 이런 작업에 고려 | 추론 수준 제안 |
| --- | --- | --- |
| **GPT-6.1 Sol** | 요구 이해부터 분석·코드 작성·오류 수정·검증까지 이어지는 주 작업 | 현재 기본값 유지. 직접 정한다면 Medium, 복잡한 오류·조건 충돌은 High 고려 |
| **GPT-6 Sol** | 여러 단계의 구현·디버깅. 이미 이 모델로 잘 진행 중이면 유지 | Medium을 출발점으로, 어려운 원인 분석은 High 고려 |
| **GPT-5.6 Terra** | 기준이 명확한 일반 처리·요약·정리의 대안이 필요할 때 | 현재 기본값 유지. 직접 정한다면 Medium 고려 |
| **GPT-6 Luna** | 정해진 항목 추출·분류·형식 변환·작은 수정처럼 정답 기준이 명확한 작업 | 화면 기본값 우선. 짧고 단순한 추출·수정만 Low 고려 |

Sol 6.1의 여러 단계 작업과 Luna의 추출·정리 용도는 [Models](https://learn.chatgpt.com/docs/models), [Model selection](https://developers.openai.com/api/docs/guides/model-selection)을 참고했다. Sol 6의 구현 용도와 Terra 5.6의 균형 지향은 각각 [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) 설명을 참고했다. **Terra 5.6을 Terra 6.1과 같은 모델로 취급하지 않는다.** 간단한 작업마다 Luna로 바꿀 필요도 없다.

### 추론 수준은 이렇게 판단하기

| 화면에 있는 수준 | 고려할 때 |
| --- | --- |
| **Low / Light** | 짧은 문구 수정, 명확한 추출·변환. 결과 확인은 그대로 수행 |
| **Medium** | 여러 조건을 반영하는 분석·구현·일반 검증의 출발점 |
| **High** | 결합·분모·예외 규칙이 얽히거나 원인을 찾기 어려운 오류. 자료와 조건을 먼저 확인한 뒤 고려 |
| **Extra High / xhigh, Max** | 더 깊은 분석이 실제로 필요하고 시간·사용량 여유가 있을 때만. 기본값으로 올려 두지 않음 |
| **Ultra** | 단순한 상위 추론 단계로 취급하지 않음. 하위 에이전트를 사용하므로 이 자료집의 기본 흐름에서는 선택하지 않음 |

지원 수준·기본값은 모델과 클라이언트마다 다르다. 같은 High도 모델 간 동일한 성능·소모량을 뜻하지 않는다. 추론을 높이면 복잡한 작업에 도움이 될 수 있지만 시간·토큰 사용이 늘 수 있다. 답을 짧게 쓰라는 요청과 실제 추론 설정 변경도 별개다. [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning), [Models의 추론 안내](https://learn.chatgpt.com/docs/models#pick-a-reasoning-effort)

**바꾸기 전에는 오류 원인부터 본다.** 업무 기준이 없으면 담당자에게 확인하고, 파일·도구 오류면 그 원인을 고친다. 정보 부족을 High로 해결하려 하지 않는다. 변경이 필요하면 이유와 선택지를 짧게 제안하고 허용된 기존 선택 기능으로만 진행한다. AI가 채팅으로 “High로 하겠다”고 말한 것만으로 실제 설정이 바뀌었다고 보고하지 않는다. 선택을 위해 새 세션·설정 파일 수정·업데이트·API 연결을 추가하지 않는다.

확인일: **2026-10-31**. 연결된 공개 공식 문서의 관련 본문을 직접 읽었다. API의 기본값·가격·지원 도구를 시험 화면의 설정·과금·권한으로 옮기지 않는다. 문서의 작업별 추천은 실전 비교나 점수·절감률을 검증한 결과가 아니다.
