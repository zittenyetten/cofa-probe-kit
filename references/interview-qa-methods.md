# 인터뷰·역할 분리·QA — 설치 없이 따라 하는 절차

**질문은 결과를 바꾸는 빈칸을 줄이고, QA는 만든 결과가 요구를 만족하는지 실제 근거로 확인하는 일이다.** 지금 필요한 절만 읽는다. 조건이 충분하면 바로 작업하고, 단순 용어 질문에 이 절차 전체를 적용하지 않는다.

이 문서는 Ouroboros(ooo)의 인터뷰·QA, Superpowers의 역할 분리 원칙과 이 자료집의 업무 질문·검증 기준을 재구성한 **방법 안내서**다. 원본 도구의 실행판이나 공식 평가 기준이 아니다. 설치·MCP·외부 검색 없이 로컬 문서로 참고하며, 실제 분석·실행·파일 생성·검증은 현재 안내가 허용한 제공 도구로 진행한다.

## 1. 인터뷰: 답에 따라 무엇이 달라지는가

| 순서 | 할 일 | 남길 내용 |
| --- | --- | --- |
| 자료 먼저 | 실제 과제 지시서·입력·이미 받은 답변을 확인한다. 파일에서 알 수 있는 사실은 먼저 읽고, 업무 정책·선호·선택은 사실 조회로 대신 확정하지 않는다. | 목표·필수 결과·제약·완료 기준과 근거 위치 |
| 중요한 빈칸 선택 | 잘못 가정하면 필수 결과가 틀리거나 큰 재작업이 생기는 조건부터 고른다. 범위·출력·예외·검증 중 한 주제에만 매달리지 않는다. | 미확인 조건 → 답에 따라 바뀔 처리·출력·검사 |
| 질문 전달 | 한 결정에 집중한 중립적인 질문을 쓴다. 같은 결정에 필요한 짧은 항목은 묶어도 된다. 업무 기준은 현업 담당자, 화면·제출 방법은 Helper, 규정 충돌은 운영 문의로 구분한다. 사람이 질문을 전달한다. | 질문과 묻는 이유 |
| 실제 답 반영 | 받은 답의 범위만 갱신한다. 답변의 조건·예외·이유를 짧은 요약에서 누락하지 않는다. 결과를 바꿀 만큼 해석이 애매할 때만 좁혀 확인한다. | 확인된 내용 / AI 해석·제안 / 남은 미확인 |
| 작업으로 전환 | 목표·필수 출력·핵심 규칙·검증 방법이 충분하면 질문을 끝낸다. 남은 조건에 영향받지 않는 작업은 먼저 진행한다. | 먼저 만들 작은 결과와 확인 방법 |

**원문 요구 / 담당자 답변 / AI 추가 제안 / 사용자의 실제 결정**은 구분한다. 설명을 이해했다는 사실과 데이터·구현을 검증했다는 사실도 다르다. AI 제안이 저절로 필수 요구나 사용자 결정이 되지는 않는다. 정해진 질문 횟수나 매 답변마다 재승인받는 절차는 없다.

### 답이 애매할 때만

| 상황 | 다음 행동 |
| --- | --- |
| “빠르게”, “정확하게”처럼 모호함 | 실제 사용 상황·판단 지표·경계 사례로 좁힌다. AI가 목표 수치를 만들어 넣지 않는다. |
| 일부만 답함 | 답한 부분만 갱신한다. 빠진 조건이 결과를 바꾸면 그 부분만 묻는다. |
| 모름·자료 없음 | 필요하면 다른 확인 경로를 한 번 확인한다. 경로가 없으면 해당 결정은 보류하고 다른 중요한 질문·독립적인 작업을 이어간다. |
| 자료·답이 충돌함 | 적용 대상·기간·권한·명시적 정정 여부와 결과 차이를 확인한다. 나중에 읽었다는 이유만으로 우선하지 않는다. |
| 충분히 구체적임 | 추가 질문을 만들어내지 않는다. 작업 중 새 모순이 생기면 그 조건만 다시 확인한다. |

일반 질문 예시는 “값이 없는 기록은 어떤 상태이며 결과에 어떻게 반영해야 하나요?”다. “빈 값을 0으로 넣으면 되죠?”는 정책을 먼저 정하고 동의를 유도하므로 피한다. 구체적인 질문 예시·실제 답 반영·선택적 인계 문구는 [RUNBOOK의 인터뷰 안내](../RUNBOOK.md#실전-업무-인터뷰-루프)에 있다.

## 2. QA: 무엇과 비교해 맞다고 판단했는가

먼저 **현재 결과 파일·적용한 입력과 조건·필수 요구**를 맞춘다. 이전 버전의 통과 기록이나 “완료했습니다”라는 출력만으로 현재 결과를 통과시키지 않는다. 검토만 요청받았다면 결함·근거·수정 제안을 보고하고 파일은 바꾸지 않는다. 이미 요청받은 수정은 그 범위 안에서 진행한다.

| 순서 | 할 일 | 판단 기준 |
| --- | --- | --- |
| 기준 연결 | 필수 요구마다 관찰 가능한 기대 결과와 검사 방법을 정한다. 기준은 지시서·확인된 업무 규칙에서 가져온다. | 요구 → 검사 입력·방법 → 기대 결과 |
| 실제 결과 검사 | 파일이 존재하는지뿐 아니라 내용·형식·범위를 읽는다. 동작이 있는 결과물은 허용된 기존 도구로 해당 동작을 실행한다. 문서는 내용·근거·누락을 대조한다. | 실제 관측과 근거 위치. 실행하지 못한 동작은 미검증 |
| 다른 방법으로 대조 | 원자료의 작은 사례를 직접 계산하거나 구현과 다른 방식으로 비교한다. AI의 동의·같은 코드 재실행만으로 독립 검증했다고 하지 않는다. | 예상과 실제의 차이. 합계가 같아도 행별 대응은 따로 확인 |
| 실패 우선 처리 | 필수 출력 누락·업무 규칙 위반·잘못된 성공 표시처럼 결과에 직접 영향을 주는 문제부터 다룬다. 수정 요청 범위이면 고친다. | 실제 실패가 있으면 AI 평가가 좋아도 해당 요구는 실패 |
| 수정 후 재검사 | 실패했던 사례와 수정에 영향받는 관련 요구를 다시 확인한다. 입력·정책이 바뀌었으면 기대 결과도 재검토한다. | 현재 조건에서의 관측. 이전 통과를 그대로 재사용하지 않음 |

정확성·필수 내용의 완전성·사용 목적·도메인 기준에 맞춰 **해당 검사만** 고른다. 데이터라면 누락·중복·결합 후 행 증가·단위·분모·경계값을 보고, 빈 값·미확인 상태를 임의로 0이나 정상으로 바꾸지 않는다. 표가 하나인 과제에 서비스·대시보드를 추가할 필요는 없다.

### 해당 기능이 있을 때만 볼 경로

| 경로 | 기대와 실제를 비교할 것 |
| --- | --- |
| 정상 | 원자료·알려진 작은 사례와 실제 결과의 일치 |
| 실패 | 허용된 실패 입력·오류 조건에서 잘못된 성공 표시나 조용한 누락이 없는지 |
| 대체 결과 | 대체값·추정값·임시 결과의 허용 조건과 출처·상태를 확인하고, 최종 화면·파일에서도 실제 결과와 구별되는지 |
| 재시도 | 복구 후 올바른 결과·상태로 바뀌는지, 이전 오류 표시·중복 처리·누락이 남지 않는지 |
| 저장 | 요구한 저장 범위에 맞춰 새로고침·재접속 후 필요한 값이 남는지. 저장 성공 표시만으로 유지된다고 판단하지 않음 |
| 권한 | 허용된 시험 계정·자료로 사용자 A가 B의 데이터를 조회·수정할 수 없는지. 버튼 숨김만으로 서버의 접근 제한을 입증하지 않음 |
| 같은 요청 반복 | 같은 요청을 두 번 보냈을 때 요구한 중복 처리 규칙을 지키는지. 원자료·기존 결과에 영향을 주지 않는 허용된 검사 범위에서 확인 |

이 표 때문에 없는 기능을 새로 만들거나 실제 서비스를 임의로 중단하지 않는다. 업무상 허용되는 반복과 막아야 할 중복을 먼저 구분한다. 허용된 범위에서 확인할 수 없는 경로는 **미실행·보류와 이유**를 남긴다. 파일·API 검사로 화면 조작을 대신했다면 UI는 미검증이다.

검사 기록은 `요구 | 기대 | 실제 관측 | 근거 위치 | 미실행·통과·실패·보류` 정도면 된다. 전체 과제 완료는 필수 요구 전체를 대조한 뒤 말하며, 일부 통과를 전체 통과로 확대하지 않는다. 수행 못 한 검사는 실패와 구분하되 통과로 세지 않는다. 기록이 필요하면 과제 공간의 기존 WORKLOG 한 개에 이어 쓰고 공개 자료집에는 넣지 않는다.

**멈출 때:** 필요한 검사가 통과하면 마무리한다. 실패하면 수정 후 관련 검사를 반복하고, 기준·자료·환경이 없어 확인할 수 없으면 그 항목만 보류하고 이유·영향·가능한 다음 행동을 알린다. 전체 절차나 이미 통과한 무관한 검사를 계속 반복하지 않는다.

## 3. AI에게 요청하는 방법과 스킬의 차이

[RUNBOOK의 방법론 참고 요청문](../RUNBOOK.md#설치-없이-인터뷰qa-절차만-참고하기)을 필요한 때 복사한다. 인터뷰만 필요하면 1절, 결과 검사만 필요하면 2절로 범위를 좁히면 된다. 기존 시작 문구와 같은 세션에서 이어가며, 문서 전체를 매번 다시 읽을 필요는 없다.

| 형태 | 이 자료집에서의 역할 |
| --- | --- |
| 방법론 MD | 사람이 보거나 AI에게 읽혀 따르는 절차·판단 기준. 이 문서가 해당한다. |
| SKILL.md | 언제 적용할지와 수행 원칙을 정리한 스킬 형식. 기존 [task-evidence-check](../skills/task-evidence-check/SKILL.md) 하나가 필요한 때 이 문서를 참조한다. Clone만으로 자동 발견·실행을 보장하지 않는다. |
| 실행 프로그램·하네스 | 도구 호출·상태 저장·실행 제어 등을 코드로 처리하는 구성. 이 MD를 읽는 데 필요하지 않다. |

요청 작성법·스킬의 빈 구조·요청 템플릿은 [프롬프트·스킬·템플릿 안내](prompt-skill-template-guide.md)에 모았다. 현재 절차와 중복되는 새 스킬을 추가할 필요는 없다.

## 4. 역할 분리: 작업과 검토의 관점 나누기

**기본은 같은 제공 AI가 정리 → 작업 → 검토를 순서대로 수행하는 방식**이다. 실제로 다른 에이전트를 호출하는 기능은 필요하지 않다. 단순 작업에 역할별 긴 대화·보고서를 만들지 않고 필요한 관점만 적용한다. 복사할 문구는 [RUNBOOK의 역할 분리 요청문](../RUNBOOK.md#설치-없이-역할을-나누어-작업검토하기)에 있다.

| 역할 | 맡을 일 | 넘길 내용 |
| --- | --- | --- |
| 진행 정리 | 실제 지시서·이미 받은 답·현재 결과를 읽고 작업 범위와 의존 관계를 정한다. 업무 미확인을 임의로 결정하지 않는다. | 목표·필수 요구·제약·입력/결과 위치·검사 기준·미확인 |
| 작업 | 요청받은 범위의 분석·구현·파일 생성을 하고 해당 검사를 수행한다. 원자료는 보존한다. | 결과 위치·변경 내용·실행한 검사와 실제 관측·남은 문제 |
| 검토 | 원문과 실제 결과를 읽고 아래 두 관점으로 판단한다. 검토 단계에서 결과 파일을 바꾸지 않는다. | 요구 충족 판정 / 품질·검증 판정, 각각의 근거와 필요한 수정 |

검토는 **① 요구 충족: 누락·요구 오해·불필요한 추가가 있는가 → ② 품질·검증: 실제 결과가 맞고 검증 근거가 충분한가** 순서로 한다. 검토자 두 명을 반드시 만드는 뜻은 아니다. 작업 담당의 완료 보고만 믿지 않고 원문·결과·검사 기록을 대조한다. 실제 검사가 필요한지는 [QA 절차](#2-qa-무엇과-비교해-맞다고-판단했는가)로 판단한다.

검토 후에는 진행 정리 관점에서 지적의 근거와 요구상 중요도를 판단한다. 이미 요청받은 수정은 작업 단계에서 고치고 영향받는 부분을 재검사한다. 검토만 요청받았다면 지적과 수정 제안까지만 보고한다. 기준이 없어 판단할 수 없으면 보류하고 필요한 확인만 제시한다. 여러 작업을 합친 뒤에는 개별 통과 외에 필수 결과 전체의 누락·연결도 확인한다.

**같은 AI의 순차 검토는 자기검토다.** 역할 이름을 달거나 “검토자가 동의했다”고 출력하는 것만으로 별도 에이전트가 실행되거나 독립 검증이 성립하지 않는다. 실제로 읽고 실행한 근거만 보고한다. 별도 에이전트도 동일한 오판을 할 수 있으므로 원자료 대조·다른 계산 등 관측 근거를 대신하지 못한다.

### 실제 내장 하위 에이전트는 선택 사항

이미 제공된 기능이고 현재 안내상 사용 가능함이 확인된 경우에만 별도 작업·검토 담당으로 나눌 수 있다. 기능이나 허용이 미확인이면 이를 시험하거나 새로 설치하지 않고 같은 세션의 순차 검토를 사용한다. 외부 모델·새 계정·새 창으로 연결하는 대안은 만들지 않는다. 이 역할은 작업 AI 안의 분담이며 현업 담당자의 실제 답변을 대신 만드는 역할이 아니다.

- 전달할 범위는 해당 작업의 원문 요구·정확한 조건, 입력/결과 위치, 수정 가능한 파일, 기존 결정·의존 관계, 검사 기준·미확인이다. 원문 위치만 주고 접근할 수 있다고 가정하지 않는다. 같은 세션에서는 기존 문맥을 이어 쓰며 매번 인계 문서를 만들지 않는다.
- 작성 담당은 한 번에 하나로 두고, 검토 담당은 읽기 위주로 둔다. 검토 중인 결과를 동시에 수정하지 않는다. 수정되면 검토 대상 버전과 관련 검사를 갱신한다.
- 병렬화는 공유 상태·파일 충돌·선행 결과 의존이 없는 읽기 조사·검토에 한정한다. 작업과 그 결과의 검토는 순서대로 진행한다. 합칠 때도 전체 결과를 확인한다.
- 실제 호출 여부와 각 담당이 읽거나 검사한 범위를 구분한다. 호출하지 않았다면 역할별 대화를 만들어낸 뒤 “다중 에이전트 검증 완료”라고 보고하지 않는다. 기록은 기존 WORKLOG 하나에 필요한 부분만 남긴다.

## 출처와 재구성 범위

2026-10-30에 아래 공개 원문을 직접 읽고 필요한 판단 원칙만 요약했다. 출처는 확인용이며 사용 중 인터넷으로 열 필요가 없다.

- [Ouroboros interview](https://github.com/Q00/ouroboros/blob/722172ef096767583679d04aef5e847458fee6b2/skills/interview/SKILL.md): 자료로 확인할 사실과 사람의 판단을 구분하고, 답의 조건·이유를 보존하며, 여러 미확인을 함께 관리하는 원칙을 참고했다.
- [Ouroboros QA](https://github.com/Q00/ouroboros/blob/722172ef096767583679d04aef5e847458fee6b2/skills/qa/SKILL.md): 대상·기준을 정하고 실제 관측을 AI 판정보다 우선하며 수정 뒤 다시 검사하는 원칙을 참고했다.
- [Superpowers subagent-driven-development](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/subagent-driven-development/SKILL.md): 작업·검토를 구분하고 요구 충족·품질을 확인한 뒤 전체 결과를 검토하는 원칙을 참고했다. 이 버전은 작업 검토 담당이 두 관점을 함께 평가한다.
- [Superpowers dispatching-parallel-agents](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/dispatching-parallel-agents/SKILL.md): 범위·입력·기대 출력을 좁혀 전달하고, 의존·공유 상태가 없는 일만 병렬로 다루는 원칙을 참고했다.
- 업무 질문 예시·응시 동선·경로별 검사·기록 형식은 이 자료집의 기존 원칙을 통합한 작성 제안이다. 업무 질문의 기존 출처는 [RUNBOOK](../RUNBOOK.md#실전-업무-인터뷰-루프)에 남겼다.

OOO의 점수 임계값·Seed 생성·매 단계 승인·여러 에이전트 호출·도구 설치·자동 반복 체계는 옮기지 않았다. 이 문서를 읽는 것은 `ooo interview`나 `ooo qa`를 실행한 것과 같지 않으며, 점수·시험 호환성·경고 방지를 보장하지 않는다. AI가 금지된 단계에는 사용하지 않는다.

Superpowers의 실제 하위 에이전트·worktree·모델 변경·Git 작업·별도 기록 파일·자동 반복 체계도 필수 절차로 옮기지 않았다. 같은 세션의 순차 검토와 읽기 중심 병렬화 제한은 이 자료집의 사용 범위에 맞춘 작성 제안이다. 원문의 조정자 판단 권한을 미확인 업무 정책·수치의 확정 권한으로 확대하지 않는다.
